# 同行调研与第二轮优化：让 agent 看见结果、少读无用信息（2026-11-05）

续 [agent-adaptation-ab-2026-11-05.md](agent-adaptation-ab-2026-11-05.md)。本文回答两个问题：同行在做什么、哪些值得学；按“改动最小、收益最大”的原则做了哪些改动，以及改动后测到了什么。

## 结论

- **最值得学的是反馈，不是脚手架。** 外部消融的结论一致：对 agent 的 CAD/CAE 结果帮助最大的，是渲染出来的多视图，以及按需求逐条给出的通过/失败和余量。脚本化的反思和角色拆分收益很小（[arXiv 2609.03718](https://arxiv.org/html/2609.03718v1)）。
- **我们原来恰好把最有价值的反馈关掉了。** 服务端建议迭代时用 `response_detail: "compact"`，而 compact 会去掉四视图缩略图，只留下约 1.4k token 的 feature graph。在此前全部 9 次试验里，agent 一张图都没有收到。
- **本次 4 处小改动之后**（每组 3 次，无头 Claude Code，同一个支架任务）：任务成功率保持 3/3；工具返回的文本从 71.7k 降到 51.4k 字符/次（−28%）；每次运行收到 1–2 张四视图；中位成本从 $0.324 降到 $0.291。成本只降约 10%，因为大头是多轮对话的缓存读取，不是单次工具返回。

## 外部证据

| 来源 | 测到的东西 | 对我们的含义 |
|---|---|---|
| [CADSmith, arXiv 2603.26512](https://arxiv.org/html/2603.26512) 表 I | 去掉渲染图后，复杂零件（T3）的平均 Chamfer 距离从 1.42 升到 49.68；在简单零件上影响不大 | 视觉校验对复杂件最关键 |

## 我们自己的测量：token 花在哪里

数据来自 `fix` 组 3 次运行的转录（每次运行的工具返回文本合计约 71.7k 字符）：

- **建模和改参数占一半。** `cad.execute_build123d` 返回 11.8k 字符，`cad.edit_parameter` 每次调用约 10k；其中 feature graph 约 5.7k。
- **缩进约占 30%。** MCP 返回的 JSON 以 `indent=2` 输出，这部分全是空白。
- **图像为零。** compact 模式关掉了缩略图，而一张 480 px 的四视图只有约 300 个图像 token。

## 本次改动（都在现有接口内，没有新工具）

1. **MCP 返回去掉缩进**（`mcp_server._coerce_result`）。前端走 REST，不受影响。
2. **compact 保留四视图**，只有显式传 `thumbnail: false` 才省略（`_should_render_thumbnail`）。
3. **compact 不再返回 feature graph**（建模、改参数、替换/删除零件四处）；`editable_parameters` 摘要和全部判定字段（`regression_diff`、`critique_diff`、`geometry_report_summary`、`modeling_fidelity`）保留。完整的图仍可通过 `cad.list_editable_parameters` 和 `aieng.agent_context` 获取。
4. **`cae.extract_solver_results` 返回 `acceptance_verdict`**：只要记录了验收准则，就直接列出未通过的需求（指标、比较方式、期望值、实测值、状态）。没有准则时响应保持不变。此前这个判定只出现在约 8k token 的 `aieng.agent_context` 里。本次支架任务没有设置验收准则，所以 A/B 测不到这一项，只有单元测试覆盖。

| 组 | 成功 | 中位成本 | 中位工具调用 | 工具返回文本/次 | 收到的图像/次 |
|---|---|---|---|---|---|
| 精简契约 + 只读修复（`fix`） | 3/3 | $0.324 | 17 | 71.7k | 0 |
| 再加本次 4 项（`lean2`） | 3/3 | $0.291 | 18 | 51.4k | 1–2 |

两组的应力和位移变化一致（约 −40.5% / −51.6%），可信度说明的覆盖面也相同。每组只有 3 次，成本差异只是方向性的。

## 与原生 agent 的直接对比（悬臂梁，有解析解）

前面的 A/B 只比较了工作台的不同版本。这里改为直接比较：同一模型（Sonnet 5.5）拿到完全相同的任务，一组用工作台，另一组只有 shell 和相同的库（build123d、gmsh、CalculiX）。按 Euler–Bernoulli 解析解评分。只评挠度：峰值应力出现在固定端边缘的奇点处，正确的 3D 模型也会比梁理论高约 20%。

| 组 | 挠度误差（10 mm / 20 mm） | 工具调用 | 输入 token | 成本 |
|---|---|---|---|---|
| 原生 agent | 3/3 在 0.7% 以内 | 10 | 0.54M | $0.338 |
| 工作台（本 PR 之前） | 3/3 在 0.6% 以内 | 19 | 0.97M | $0.292 |
| 工作台（本 PR 之后） | 3/3 在 0.6% 以内 | 17 | 0.74M | $0.279 |

- **在教科书问题上，工作台没有更准。** 原生 agent 自己就用了二次单元（`setOrder(2)`）或手写的六面体网格，没有掉进线性四面体的陷阱。现在的模型已经学会了这类基准所考的东西。这与 2026-09-07 的结论一致：价值不在计算本身。
- **工作台多花的调用来自引导和逐步求解。** 原先每次运行还会因 `cad.edit_parameter` 不认 agent 自己写的部件名和常量名，多出一次被拒和一次查询。本 PR 修掉了这一点，并让 `cae.run_simulation_pipeline` 默认写入新的 run、不覆盖旧结果，成为一步重算的安全路径。
- **工作台的增量在复核上。** 一次工作台运行主动做了网格收敛研究，原生 agent 一次都没有做。这是可信度上的差别，不是准确度上的差别，而这类简单任务测不出它的价值。

**结论：** “装上后比原生 agent 强很多”在简单任务上不成立，必须在原生 agent 会出错的任务上去证明。合适的候选包括：带螺栓孔和斜面的受载选择、修改后需要重新绑定的迭代、薄壁件的网格充分性，以及带验收准则的多工况。下一步应先设计这样一组任务并跑同样的对比，再决定往哪里加强。

## 最大的缺点：agent 要手工驱动我们的内部状态机

**现象。** 每做一次分析，agent 都要依次调用 mesh → deck → solve → extract 四个工具，还要自己管理 run id（`run_001`、`run_002`、是否覆盖）。服务端再用一组拒绝码来拦截做错的步骤（`stale_mesh`、`stale_deck`、`run_id_conflict`）。原生 agent 写一个脚本就完成了，这正是悬臂梁对比中我们多出来的调用次数的来源。

**修法：让正确的路径成为唯一的默认路径。**
- **一次调用完成分析。** `cae.run_simulation_pipeline` 本来就把各步串在一起，现在让它在网格缺失或早于当前几何时自动重新划分网格（沿用上次的尺寸），每次写入新的 run，并直接返回指标、网格精度等级、验收判定和 `change_since_previous_run`（与上一次 run 的前后对比）。
- **契约随之简化。** 修改几何后再调用一次即可。逐步调用的工具仍然保留，供需要细节控制时使用。

**真实循环里还暴露了两个缺陷，一并修复：**
1. **重新调用 `cae.setup_static` 不生效。** 新的 `@face:` 指针会产生一个新的 NSET（`LOAD_001_2`），旧的 NSET 仍绑定在已退役的面上，求解器输入因此一直被拒。agent 只能手写 `cae_mapping.json` 绕过去，而这又破坏了 run 之间的可比性。现在重新指定的指针会**移动**原有的 NSET，不再留下孤立条目。
2. **显式指针在几何修改后找不回原来的面。** 原因是 agent 只能用指针，因为 "top" 选中的是底板而不是肋顶，而指针没有可以重新解析的词语。现在建模时会一并记录面的特征（类型、法向、面积、半径），修改后只要恰好有一个面与之匹配，就能找回；匹配到多个面时仍然拒绝。

**还有一处顺手的改进。** 不带 `mesh_sizes` 调用 `cae.mesh_convergence` 时，现在以当前网格作为最细一级，再加两级按 √2 加粗的网格，不再直接拒绝。9 次运行中有 3 次就这样调用过。

**结果（每组 3 次）：**

| 任务 | 组 | 成功 | 中位调用次数 | 中位成本 |
|---|---|---|---|---|
| 悬臂梁 | 原生 agent | 3/3 | 10 | $0.338 |
| 悬臂梁 | 工作台，一次调用循环 | 3/3 | 14 | **$0.227** |
| 支架修改 | `main` | 3/3 | 29 | $0.664 |
| 支架修改 | 一次调用 + 绑定修复（pipe5） | 3/3 | 14 | **$0.234** |

- **悬臂梁：** 工作台现在比原生 agent 更便宜，速度相当（126 s 对 125 s），三次运行都主动做了网格收敛研究。
- **支架：** 修改后的重新分析全部一次完成，没有一次被拒，也没有手写的映射文件。其中一次运行是靠面的特征找回了用指针绑定的面。
- **局限：** 每组只有 3 次，成本差距只能看作方向性的。

## 第三轮：把剩余的入门和读回成本压下去

**依据。** 从最新的 9 次运行看：入门要调 readme 和两个 guide，加上两次 ToolSearch，每次运行 5 次调用、约 16k 字符，而原生 agent 几乎为零。agent 不传 `response_detail` 时，`cad.edit_parameter` 默认返回完整结果，约 6k 字符。另外，文献中最常见的失败是“能跑但解错了物理”，主要是边界条件错误（[arXiv 2605.09360](https://arxiv.org/pdf/2605.09360)、[ALL-FEM 2603.21011](https://arxiv.org/pdf/2603.21011)）。

**改动：**
1. **一次入门。** `aieng.agent_readme` 直接返回 CAD 和 CAE 契约，读一次即满足 `cad`/`cae` 的 guide 要求。readme 中的 `version_surface` 只保留版本号，去掉 2k 字符的兼容策略和哈希。服务端说明缩短一半，并列出核心工具，便于一次加载齐全。
2. **CAD 工具在 MCP 上默认返回精简结果。** 只在 MCP 边界生效，REST 和 UI 保持完整默认；agent 需要时可以传 `full`。
3. **pipeline 结果附带 `setup`。** 用工程语言写明实际绑定了什么（材料、哪个面固定、载荷作用在哪个面上），与数字放在同一次返回里，便于当场核对意图。复用了已有的 `_describe_cae_setup`。
4. **说明 pipeline 已包含前后对比，不需要再调 `cae.compare_runs`。** 上一轮每次运行都多调了这一次。这一条在测量之后才改，尚未复测。

**结果（每组 3 次，改动 4 之前）：**

| 任务 | 组 | 调用 | 轮次 | 时长 | 成本 | 输入 token |
|---|---|---|---|---|---|---|
| 悬臂梁 | 原生 agent | 10 | 11 | 125 s | $0.338 | 0.54M |
| 悬臂梁 | 上一轮 | 14 | 15 | 126 s | $0.227 | 0.66M |
| 悬臂梁 | 本轮 | 12 | 13 | 135 s | $0.213 | 0.58M |
| 支架修改 | `main` | 29 | 30 | 364 s | $0.664 | 2.12M |
| 支架修改 | 上一轮 | 14 | 15 | 252 s | $0.234 | 0.67M |
| 支架修改 | 本轮 | 12 | 13 | 148 s | $0.214 | 0.60M |

全部成功。悬臂梁的输入 token 已与原生 agent 接近，成本低约三分之一，而且每次运行都附带网格收敛检查。支架任务里每次运行仍会因为 `PLATE_T` 是全局参数而多一次 `scope_risk` 确认；这是按设计拦截改动范围的风险，保留不变。

## 没有做的事和原因（按收益/代价排序的建议）

1. **一次性加载工具的客户端仍要付约 36k token 的工具定义成本**（98 个工具）。Claude Code 按需加载工具，所以本次测不到这一项。Codex 等客户端会一次加载全部。已有 `--compact-tool-surface`（35 个工具，约 13k token），但需要手动开启。下一步可以让安装文档对这些客户端默认推荐它，或者合并低频工具。这是中等改动，应当先在一个一次性加载工具的客户端上做测量。
2. **用 Hephaestus-CCX 做 CAE 闭环的外部基准。** 它的需求判定与我们的 `acceptance` 同构，是证明“比裸 agent 更强”最直接的外部证据，可以与 CADGenBench（brief 中的任务 A）互补。
3. **CAE 返回的精简。** `cae.run_solver` 和 `cae.generate_solver_input` 每次仍有约 4k 字符，主要是 `receipt` 和 `changed_artifacts`。仿照本次 CAD compact 的做法，是下一个小改动。
4. **agent 从不点名 `credibility` 等级。** 12 次运行中一次都没有，尽管契约要求这样做。可能是因为可信度不在 agent 读取数字的那个响应里。可以把可信度等级放进 `cae.compare_runs` 和提取结果的顶层，改动很小，但需要先确认这些响应里目前是否已经有它。
5. **代码模式（code execution with MCP）。** 收益可能很大，但需要新的执行边界和安全评审，属于大改，等前 4 项有了结论再说。

## 边界

- 外部论文的数字只读了相关表格；build123d-mcp 和 CADSmith 的数字是项目自报。
- A/B 只覆盖 Claude Code（Sonnet 5.5）和一个任务，每组 3 次。
- “看到图像会让结果更好”这一点，本任务测不出来：支架几何简单，两组都 3/3 成功。外部消融显示，收益集中在复杂零件上。
